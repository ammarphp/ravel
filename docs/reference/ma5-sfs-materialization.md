# MA5 SFS source materialization

An ordinary `mode: analyze` study can use `task.backend: routine-build` with a
schema 6 `kind: ma5-sfs-materialization` input. This phase generates the source
needed by a supplied expert analysis from its original Simple Fast Simulation
(SFS) card. It retains the analysis, registration, Main, build files and every
generated member through the existing supervised worker and review lifecycle.

The input binds four ordinary assets (`source`, `header`, `info`, `sfs_card`),
one complete selected MA5 1.11.1 source projection, an explicit interpreter and
runtime-file census, a declared writer architecture, and execution/storage
budgets. The source/header analysis names must agree. The header must depend on
the generated smearer and tagger headers. The ordered card admits literal
`main.fastsim` settings and smearer, reconstruction-efficiency and tagger
definitions. Import, submit, install and compound commands are refused.
Efficiency expressions remain original card inputs; intake does not establish
their detector calibration or physical applicability.

`routine_build.seal_configuration`, `inputs`, `build_plan` and
`execution_seconds` perform source admission without importing MA5 or running
its writers. Ordinary planning requires science schema 2, one attempt, zero
redos and an explicit review policy. Supply the original goal binding when
this phase belongs to a larger physics request. Source preparation establishes
neither approval nor materialization.

After ordinary approval, one isolated interpreter calls the pinned upstream
`Main`, `Interpreter` and `JobWriter` APIs. It reads the exact SFS program,
uses the upstream header/source writers, runs `newAnalyzer.py` within that same
interpreter, replaces only its analysis stubs by the supplied source/header,
and writes Main with the `analysis.saf` name used by the existing MA5 analysis
consumer. The normal MA5 launcher performs configuration and library-build
work during startup, so this phase directly composes its writer APIs and bars
implicit subprocess, compiler, installer and event dispatch. The supplied original SFS formulas and headers remain source inputs.

The complete output census must include nonempty `new_smearer_reco.h/.cpp`,
`sigmas.h`, `reco.h`, `new_tagger.h/.cpp` and `efficiencies.h`, the exact supplied
analysis and metadata, single analysis registration, FastJet/smearer/tagger
Main construction, Makefile and setup files. The receipt binds the original
and staged source, actual writer/import observation, interpreter, request,
supervised execution evidence and all job members. Revalidation checks those
semantics again. Original inputs and generated documents are captured with
bounded stable reads; successful delivery includes its completion receipt in
the storage ceiling. Failed evidence is retained.

Every staged original asset is captured against the intended original bytes
before the writer starts and rechecked after it exits and through completion.
The complete generated file/directory population is captured before job
inspection and must stay unchanged through the final receipt write. Late
headers, setup scripts, unknown files or empty directories cause failure;
they are retained as evidence and never folded into a rebased success census.

The source projection includes the selected Python/C++ writers, particle
definitions and four cached SampleAnalyzer libraries, within 32 MiB and 4096
files. It is a declaration for this writer phase, not a universal compiler or
environment closure. Declared ROOT/FastJet architecture and cached libraries
do not establish successful imports, ABI compatibility or execution.

The returned `ma5-sfs-materialization-receipt` has
`phase: materialized_source`, `compiled: false`, `native_events_processed: 0`,
`qualified_native_runtime: false`, `physics_validated: false` and
`original_task_complete: false`. It is not a completed native-build receipt.
Compilation must bind the generated job and full matching compiler/linker,
external headers/libraries and loader evidence in a separately approved
phase. The existing MA5 supplied-event route then requires that qualified
build, complete event/weight custody and native output checks. Neither phase
recovers missing published control-region data, certifies a hypothetical
joint tagger or supplies an SVJ likelihood by itself.

The portable controls use synthetic writer outputs and inert worker authority.
They exercise real ordinary planning and common report code, source and
registration reconciliation, missing/empty member refusals, source mutation,
and ending receipt revalidation. They never import MA5, compile or process
events. Actual writer, compiler, ABI and physics qualifications remain separate
empirical obligations.
