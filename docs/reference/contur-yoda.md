# Supplied-YODA Contur operation

The ordinary schema2 `contur-yoda` mode prepares fresh single-point inference from supplied YODA with pinned Contur source/runtime/user assets. It uses the existing native supervisor and returns the complete native SQLite/column delivery through the existing decoder. Exact requested settings, staged scientific inputs and ending writable-user changes are recorded. Runtime/SDK/SQLite compatibility (installed3.1.4 versus selected3.1.5), normalization, statistical applicability and scientific qualification remain open. No execution is authorized by this source integration.


The new input-document schema3 uses this same ordinary mode and supervisor for a declared `single` or `grid` operation. An explicit `profile` selects raw native modes: `default3` is SMBG/EXP/HLEXP, `full4` adds DATABG via `--databg`, and `no-exp2` is SMBG/HLEXP via `--no-exp`. Cached imports retain input schemas1/2 and add schema3 for the explicit two-mode census. These profiles retain the released confidence/complement semantics and raw missing likelihood fields; the adapter does not recompute confidence or permit absent native CLs to become zero evidence.

Every schema3 document binds its literal source attribution, configuration, complete source/data/user manifests, runtime interpreter and dependency inventory, explicit effective settings and one aggregate native resource ceiling. Native calls remain serial (`--nomultip`). The original offline setting is false; an explicitly requested true value records citation/presentation differences. A false-to-true fallback is admitted only when the authenticated released `get_inspire` call changes that setting alone and returns the source-defined `Offline` result. A failed URL query returning `Failed` is retained without relabeling it as that fallback. Other setting drift refuses delivery.

A grid additionally declares a complete manifest, ordered native beam IDs, beam selection (`all` or the exact declared list), native filename tag, and complete logical point list. Each point binds its full literal parameter dictionary and one association for each declared beam. Each association lists all original source YODAs, the expected native post-merge YODA names, and the per-native-input event count. All parameters in each original `params.dat` must agree with the declared point, including coordinates beyond plotting axes. The reusable bounds are128 points,32 beams,4,096 regular input members and512MiB total input-grid bytes. The original four-point/four-beam example is an acceptance fixture within these bounds.

Preparation copies the entire grid into a fresh owned workspace. The released `process_grid`/`process_runpoint` performs its own cleanup, merging, all-beam grouping, pool selection and statistical calculation. Initial original custody remains fixed; legitimate mutable-copy changes are disclosed rather than adopted as original bytes. Raw returns are retained before confidence checks, and the complete per-point SQLite and CSV outputs are reconciled with native grouping, full parameters, likelihood values and pool results. Ordered `yoda_info` is a list with a separate native first-entry identity/count: the database's `events_num` is not a sum over beams. Final result JSON/CSV, native artifacts, preparation and observer records are checked after ending input readback and against the original intended returned result.

The original default and Spey commands use different selection flags and signal-error/flat-uncertainty configuration. Their results do not constitute an isolated backend comparison. Pin the exact original custom configuration for a Spey task; no configuration is inferred from its label. The original grid's117 members include16 YODAs and16 parameter files with eight literal coordinates per point over7,8,13 and13.6TeV beam IDs. Source/API controls with inert point objects do not qualify real YODA decoding, SDK/SQLite compatibility, inference, normalization or physics. Approval, native admission and independent scientific review remain required separately.
