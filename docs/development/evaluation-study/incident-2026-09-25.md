# Incident 2026-09-25: harness census killed the user's login session (twice)

## Impact

Twice on 2026-09-25 (14:08:42 and 16:00:07 EDT) every process owned by the logged-in user was
killed within about five seconds: the Claude desktop app, Finder, Dock, WindowManager, every
launchd user agent and every open application. It looked like a laptop crash. macOS itself kept
running: uptime shows no reboot, and root-owned `loginwindow` and `WindowServer` survived. Work in
progress was lost only where it had not been written to disk. Uncommitted worktree changes survived
and were checkpointed.

## Evidence

- `last reboot` and `uptime`: last boot 07:37; no reboot at either time.
- launchd's unified log attributes the kills to one sender each time:
  `exited due to SIGKILL | sent by python3.12[81187]` (472 log entries for 433 distinct processes,
  14:08:42–14:08:47) and `sent by python3.12[88297]` (389 entries for 352 processes,
  16:00:07–16:00:12). Each window also has 39 `xpcproxy exited` entries; all 39 in the first window
  and 37 in the second are a second entry for a process already listed. Relaunched Dock and
  Finder processes were killed again after running 11–22 ms in the first window and 9–25 ms in the
  second (launchd's `ran for` values), i.e. by a loop, for the 5.0 s of `KILL_WAIT_S`/`CENSUS_WAIT_S`.
  (Counts and intervals re-read from `log show` over 14:08:30–14:09:00 and 15:59:50–16:00:30,
  filtered on `sent by python3.12`; the first version of this record gave the entry counts as
  process counts and the interval as 8–22 ms.)
- PID 88297 started 23 ms after an integration worker ran `pytest tests/governance` in its worktree.

## Root cause

`isolation._scan` identified a launch's subject processes by asking the kernel (private
`sandbox_check`) whether each process is denied metadata of `census-deny` and allowed metadata of
`census-allow`, two coordinator files named only in that launch's Seatbelt profile. For a path that
does not exist, `sandbox_check` answers "denied" for every process, sandboxed or not. With
`census-deny` missing and `census-allow` present, the membership test was therefore true for
roughly every unsandboxed process on the host (548 of 584 in a harmless reproduction), and the
SIGSTOP+SIGKILL rounds killed them. Root-owned processes were refused by the kernel.

- **Crash 2 (reproduced exactly):** a work-in-progress `census_launch` for lost launches recreated
  only the allow file after its test removed the marker directory
  (`test_census_of_a_sandboxed_lost_launch_kills_every_process_in_its_sandbox[True]`). Under a
  diagnostic signal guard the same test attempted 63,874 signals to 1,112 distinct processes.
- **Crash 1:** same signature (a python3.12 harness process, a 5-second SIGKILL loop, every user
  process), during several concurrent pytest sessions. It did not replay with any single suite
  alone, so the event that removed `census-deny` is unconfirmed. The defect class is the same and is
  closed by the fix.

A second, latent hazard of the same kind was the runner's post-interruption census, which matched
processes by command-line substring and killed whole groups. It was already being replaced.

## Fix (commit on `evaluation-slice`)

- `_scan` fails closed: it raises `CensusUnavailable`, signalling nothing, unless both marker files
  are intact regular files that the unsandboxed coordinator itself reads as allowed (checked before
  the scan, before every signal and after the scan), and unless a signal-free first pass finds no
  member older than the launch (every member of the launch's sandbox descends from the launch, so an
  older one means the membership test is broken; the signalling pass stops at one too). The first fix
  used a count-only pass with a `SCAN_MATCH_LIMIT` of 128 members instead; the repair wave replaced it,
  because a subject could reach that count and so turn the census off, while no subject can start a
  process older than its launch (decision E-19).
- A process is signalled only if it started at or after the launch (`proc_pidinfo` start time),
  is not pid 0/1 and is not the coordinator or one of its ancestors. `killpg` refuses pgid 0/1, the
  coordinator's own group and a group id now held by a different leader.
- When the census is unusable the launcher keeps killing its own process group only and reports
  `census_complete: false`; adapters flag `census_incomplete` and the runner records it.
- Tests: five regressions, including an end-to-end launch whose `census-deny` vanishes mid-run
  (the unfixed launcher attempted 54,999 kills in it; the fixed one kills only its subject and every
  bystander survives), and a session-wide guard in `tests/governance/conftest.py` that refuses, and
  fails the run on, any signal (other than signal 0) to pid 0/1, the test process's own group or
  ancestors, or a process that started before the test session. A target whose start time cannot be
  read (for example a group whose leader has exited) is allowed. It does not tell a process the tests
  started from one another program started during the session, so it does not protect processes that
  other sessions start meanwhile, such as a concurrent worker's pytest children (the setting of crash
  1); that is why full-suite runs stay serialized. Its process reader is bound once, before any test,
  so a test that replaces the harness's readers cannot change what it refuses.

## Prevention in the development workflow

- A diagnostic `sitecustomize` kill guard was installed in `.venv-dev` for the remainder of this
  development cycle. It refused no signal through the G1 acceptance run and was removed on
  2026-09-26 ([environment change log](../history/environment-changes.md), 2026-09-25 entry). It
  would also refuse a real host's own binary, so it must not be reinstated for a live smoke.
- Workers and reviewers may not run mutation probes or new process-killing code outside the
  guarded environment, and concurrent full-suite runs are limited.
- Any code path that sends signals must bound its targets by an independent invariant (start time,
  ancestry), not by a single predicate that can fail open.

## Residual risk

The census depends on a private macOS SPI. A future change in its semantics is caught by the intact
marker check and by `census_available()` at launch time, which then refuses sandboxed launches.
Pid reuse between a membership check and a signal remains a microsecond-scale race. It is bounded by
sequential pid allocation (a pid is reused only after the pid space wraps), not by the start-time
floor, which a new process holding a reused pid would pass.

The subject-triggerable switch that turned the census off (more than `SCAN_MATCH_LIMIT` members) is
closed: the census has no count limit. On Linux a wall-clock step moves every later start-time read
by whole seconds, so no Linux start time identifies a process across a step: the launcher compares a
clock-free identity (boot id and start ticks), and `census_launch`, which holds only the recorded
wall-clock `leader_start`, treats a holder whose start differs from it by whole seconds, or by less
than 1e-4 s on any platform, as unprovable (nothing signalled, census incomplete). The Linux path
has never run: this host is macOS, and CI (Linux) runs only on a push to `main` or a pull request,
which this branch, in a repository with no remote, has not had.

On macOS a backward wall-clock step of more than 50 ms (`START_SLACK_S`) during a launch makes every
subject process started after it look older than the launch, so the census reports itself broken:
it signals nothing further, the launcher kills only its own process group, and the run is flagged
`census_incomplete` with survivors unknown (fail closed).
